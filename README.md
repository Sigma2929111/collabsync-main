# CollabSync

**CollabSync** — плагин для **Roblox Studio**, который позволяет нескольким разработчикам совместно работать над одной сценой (place) в реальном времени. Участники подключаются к общему лобби, видят друг друга и получают синхронизированные изменения объектов, чтобы вместе собирать и редактировать проекты.

> **Статус проекта:** активная разработка. Эта ветка содержит рабочие изменения, но перед публичным production-релизом необходимы полноценные тесты в Roblox Studio и проверка серверной безопасности. Не используйте текущую сборку для критически важных проектов без собственного тестирования.

## Возможности

- Создание лобби и подключение участников по приглашению/токену.
- Синхронизация изменений объектов между подключёнными редакторами.
- Передача начального состояния сцены (snapshot) и последующих изменений (delta).
- Отображение участников и чат внутри лобби.
- Подключение через отдельные адреса серверов, в том числе для прямой/LAN-схемы.
- Интерфейс настроек, список участников, whitelist места и элементы управления доступом.
- Поддержка распространённых свойств объектов, частей, MeshPart, SpecialMesh, Decal и Texture; поддержка PBR-карт SurfaceAppearance развивается.

Фактическая полнота синхронизации зависит от типа Instance и конкретных свойств. Не все сервисы и типы объектов Roblox гарантированно поддерживаются.

## Архитектура: два способа запуска

CollabSync разделяет каталог/управление лобби и WebSocket-канал синхронизации.

### 1. Стандартная схема — Server 1 + отдельные Server 2

Это основной вариант для независимого хостинга:

- **Server 1 (центральный)** — общий каталог лобби, создание и подключение к сессиям, выдача JWT-токенов и получение данных о ролях.
- **Server 2 (у каждого хоста)** — WebSocket-сервер конкретного хоста, который передаёт snapshot, изменения и события участникам его лобби.
- **Плагин** — обращается к центральному Server 1, а затем подключается к адресу Server 2 нужного лобби.

Владелец проекта может держать центральный Server 1 постоянно доступным. Пользователи запускают собственные Server 2 для своих лобби. Для лобби команды также может работать отдельный Server 2, размещённый владельцем.

### 2. Компактная схема — Server 2-in-1

**Server 2-in-1** объединяет HTTP API Server 1 и WebSocket-функции Server 2 в одном Node.js-процессе и на одном хостинге.

Этот режим предназначен для тех, кому неудобно оплачивать или поддерживать два отдельных хостинга. Он сохраняет идею каталога лобби и real-time синхронизации, но упрощает развёртывание.

## Автоподключение через Radmin VPN

Для прямого соединения без ручного ввода IP хост запускает локальный Server 2 на своём ПК (`npm run start:host`), подключается к одной сети Radmin VPN и создаёт лобби в плагине. Плагин обращается к локальному `http://127.0.0.1:3001/network-info`, получает IPv4 адаптера Radmin и автоматически публикует `http://<RADMIN-IP>:3001` как адрес WebSocket-сервера. При первом обращении Roblox Studio может запросить у пользователя разрешение плагину на связь с localhost — его нужно разрешить. Roblox официально поддерживает обращения плагинов к `localhost`/`127.0.0.1` и WebSocket-клиенты в Studio. Участник открывает вкладку «Прямое (Radmin)» и выбирает лобби из списка; адрес и JWT вводить не нужно. Endpoint обнаружения доступен только с loopback.

Если локальный Server 2 не обнаружен или Radmin VPN не подключён, плагин использует указанный URL Server 2 как резервный вариант. Для подключения по Radmin оба компьютера должны состоять в одной виртуальной сети, а входящие TCP-подключения к порту Server 2 должны быть разрешены в брандмауэре Windows. Наличие адреса в каталоге не гарантирует, что сеть/фаервол пропустит соединение.

## Долгосрочные лобби и резервные копии (экспериментально)

При создании лобби можно включить переключатель «Долгосрочное лобби». В **Server 2-in-1** сохраняются каталог, snapshot, история, журнал активности и backup-данные. В раздельной схеме **Server 1 + Server 2** теперь также сохраняются метаданные долгосрочных лобби на Server 1 и snapshot/history на Server 2; после штатного перезапуска обоих процессов владелец может вернуться к сохранённой сцене. Гости могут оставаться в долгосрочном рабочем пространстве при временном отсутствии владельца.

Файлы сохраняются атомарной записью в каталог `.collabsync-data` (или путь из `COLLABSYNC_DATA_DIR`): каталог Server 2-in-1 использует `state.json`, Server 1 — `catalog-state.json`, отдельный Server 2 — `server2-state.json`. Для раздельного развёртывания настройте постоянный диск **на каждом** сервере и задайте одинаково подходящий локальный путь `COLLABSYNC_DATA_DIR` (файлы не должны лежать на одном и том же общем сетевом диске, если файловая система не гарантирует атомарный rename). Важно: backup/activity API и UI пока доступны только в Server 2-in-1; раздельная схема сохраняет каталог и сцену, но ещё не имеет полного набора инструментов резервного копирования. Не размещайте эти файлы в публичной директории и ограничьте доступ: в них находятся данные лобби, хеши паролей, snapshot и история.

**Автоматические backup выключены по умолчанию.** Владелец может включить их через API. Интервал: от 1 часа до 30 дней; срок хранения: от 1 до 100 копий. Для управления используется Bearer JWT владельца:

```http
GET  /api/workspace/{lobbyId}/backups
GET  /api/workspace/{lobbyId}/activity
POST /api/workspace/backups/settings
POST /api/workspace/backups/create
POST /api/workspace/backups/restore
```

Пример настройки (тело JSON): `{"lobbyId":"...","enabled":true,"intervalMs":86400000,"retention":20}`. Ручная копия создаётся POST-запросом с `{"lobbyId":"..."}`; восстановление — с `{"lobbyId":"...","backupId":"..."}`. Все операции доступны только владельцу лобби. После восстановления нужно переподключить плагин, чтобы загрузить восстановленный snapshot. В настройках активного лобби владельцу доступна вкладка «Бэкапы»: включение/выключение расписания, ручное создание копии, просмотр списка, восстановление выбранной версии и краткий список последних изменений (участник, тип операции, время). При возвращении владельца долгосрочного лобби показывается сводка и предлагается принять серверную версию либо отклонить её в пользу локальной сцены.

При штатном завершении процесса (`SIGINT`/`SIGTERM`) сервер дополнительно пытается немедленно сбросить ожидающие изменения на диск. Это снижает риск потери последних изменений при корректном перезапуске, но не защищает от внезапного отключения питания или принудительного завершения процесса.

**Ограничения текущей реализации:** изменения сохраняются с debounce примерно 250 мс; это экспериментальная файловая реализация для одного процесса/узла, не кластерное хранилище. Перед production нужны тесты аварийного завершения, больших snapshot, миграций, дисковых лимитов и конкурентной записи. Не считайте её заменой полноценной БД.

## Текущий статус реализации

Это фактический статус кода в `development/release-v2`, а не обещание готовности к релизу.

**Уже добавлено, но ещё требует проверки в Roblox Studio:**
- Синхронизация snapshot/delta, список участников, чат и базовые маркеры.
- Read-only ограничения для тестеров на серверной обработке edit-delta.
- Экспериментальные долгосрочные лобби в Server 2-in-1: JSON-сохранение, восстановление после старта процесса, возврат владельца.
- Ручные и плановые backup в Server 2-in-1, список копий и подтверждение перед восстановлением.
- Проверка Bearer JWT для heartbeat/delete/backup API, проверка роли токена при WebSocket-подключении.

**Сделано частично:**
- При возвращении владельца долгосрочного лобби плагин показывает сводку изменений и предлагает принять серверную версию или отклонить её, сохранив локальную сцену. Это пока пакетное решение для всей истории: нет полноценного визуального diff по свойствам, выборочного принятия отдельных объектов и трёхстороннего слияния конфликтов.
- Backup UI пока предлагает фиксированное расписание (24 часа, 20 копий); расширенные интервалы/retention через интерфейс не настраиваются.
- Radmin/LAN — ручной ввод адреса и прямое соединение. Автообнаружения хоста, измерения качества канала и отдельной оптимизации маршрута пока нет.
- Настройки разрешений в интерфейсе не являются полноценной серверной системой ACL. Нельзя считать визуальные переключатели доказательством применения прав.
- Тестер ограничен в изменениях Place, но отдельный Play Test канал/жизненный цикл тестовой сессии не реализован.

**Ещё не реализовано:**
- Надёжная Roblox-аутентификация, подтверждающая подлинность UserId; сейчас сервер не может отличить настоящий UserId от подставленного клиентом.
- Полноценный паритет с Team Create: согласование конфликтов, locks/claim объектов, comments/tasks, история свойств и надёжное восстановление пропущенных событий.
- Diff и review изменений с принятием/отклонением владельцем до применения.
- Раздельное постоянное хранилище для Server 1 + Server 2, база данных, миграции и поддержка нескольких узлов.
- Голосовые комнаты: WebRTC signaling, SFU/TURN, push-to-talk и управление устройствами.
- Шифрование backup, лимиты диска, контроль целостности, метрики/алерты и полная проверка схем всех входящих свойств.
- Полный набор автоматических unit/integration/load tests и реальная проверка нескольких клиентов в Roblox Studio.

До закрытия этих пунктов ветка остаётся экспериментальной. Наличие функции в UI или наличие серверного endpoint не означает, что она прошла end-to-end проверку.

## Развёртывание серверов

Требуется установленный Node.js и доступный извне хостинг с поддержкой постоянного Node.js-процесса и WebSocket-соединений.

В корне репозитория уже есть `package.json` и команды запуска. Установите зависимости:

```bash
npm install
```

Для проверки синтаксиса серверных файлов:

```bash
npm run check
```

### Раздельный режим

1. Разверните файл `server 1` как Node.js-сервис. По умолчанию он слушает порт `3000`.
2. Разверните файл `server 2` как отдельный Node.js-сервис. По умолчанию он слушает порт `3001`.
3. Установите одинаковый сильный `JWT_SECRET` в окружении Server 1 и Server 2.
4. Укажите публичные адреса сервисов в настройках плагина/хостинга.
5. Убедитесь, что reverse proxy или хостинг пропускает WebSocket upgrade-запросы к Server 2.

Пример запуска (имена файлов содержат пробелы):

```bash
node "server 1"
node "server 2"
```

### Режим Server 2-in-1

1. Разверните файл `server 2 in 1`.
2. Установите переменные окружения из раздела ниже.
3. Запустите процесс:

```bash
node "server 2 in 1"
```

По умолчанию объединённый сервер использует порт `3000`.

## Переменные окружения

Задавайте секреты в панели хостинга или через защищённое окружение. Не публикуйте их в репозитории и не отправляйте в чат.

| Переменная | Назначение |
|---|---|
| `PORT` | Порт сервиса: по умолчанию 3000 для Server 1 / Server 2-in-1 и 3001 для Server 2 |
| `JWT_SECRET` | Секрет подписи JWT; должен совпадать у Server 1 и соответствующего Server 2 |
| `ADMIN_SECRET` | Секрет для административных API Server 1 / Server 2-in-1 |
| `CATALOG_PUBLIC_URL` | Публичный URL центрального Server 1 для health-проверки |
| `HOST_PUBLIC_URL` | Публичный URL отдельного Server 2 для health-проверки |
| `PUBLIC_URL` | Публичный URL объединённого Server 2-in-1 |
| `COLLABSYNC_DATA_DIR` | Каталог постоянного хранилища долгосрочных лобби и резервных копий (по умолчанию `.collabsync-data`) |
| `TESTER_IDS` | Список числовых Roblox UserId тестировщиков через запятую. Тестеры получают read-only доступ и не могут отправлять изменения Place |

**Важно:** теперь серверы отказываются запускаться, если `JWT_SECRET` или `ADMIN_SECRET` отсутствует либо короче 32 символов. Скопируйте `.env.example` в `.env` и задайте два разных случайных секрета. Не коммитьте `.env`. Для публичного развёртывания используйте HTTPS/WSS через надёжный reverse proxy и ограничьте доступ к административным маршрутам.

## Тестировщики и режим просмотра

Тестировщики задаются только числовыми Roblox UserId в `TESTER_IDS`. Декоративные статусы владельца плагина, бомбы и мусора удалены. Тестер получает обычную модель участника с отметкой `🧪 TESTER` около маркера и в чате.

Для тестера сервер подписывает read-only признак в JWT и отклоняет от него `create/update/delete/select` и отправку snapshot. Разрешены просмотр синхронизированной сцены, камера/маркер и чат. Тестер не может создавать лобби-хост и управлять участниками.

**Ограничение проверки личности:** сейчас сервер получает UserId из запроса плагина. Подпись JWT защищает права после выдачи токена, но сама по себе не доказывает, что запрос действительно отправлен владельцем этого Roblox-аккаунта. Поэтому список тестеров нельзя считать полноценной защитой от целенаправленной подмены UserId до внедрения отдельной Roblox-аутентификации. Не используйте эту схему как единственный барьер для секретных или критичных Place.

## Radmin VPN / прямое подключение

Для прямого соединения без публичного хостинга все участники и хост должны быть подключены к одной сети Radmin VPN:

1. На компьютере хоста запустите отдельный `Server 2` на порту `3001` и задайте тот же `JWT_SECRET`, что и у Server 1.
2. Разрешите входящие TCP-подключения к порту Server 2 в брандмауэре Windows. Плагин не меняет системные правила Firewall автоматически.
3. При создании лобби плагин пробует обратиться к локальному `127.0.0.1:3001/network-info`. Если сервер обнаруживает Radmin VPN адаптер, его IPv4 автоматически публикуется как адрес хоста.
4. Участники открывают **«Прямое (Radmin)»** и выбирают найденное лобби из каталога; IP и JWT вручную вводить не нужно. Для этого каталог Server 1 должен быть доступен участникам, а сам Radmin IPv4 — достижим из их VPN-сети.
5. Если лобби не появляется или не подключается, проверьте общий Radmin network, входящее правило TCP для порта `3001`, запущенный Server 2 и доступность центрального каталога. Автообнаружение работает только на компьютере хоста, где локально доступен Server 2.

Не публикуйте Radmin IP и токены в открытых чатах. Не открывайте этот порт в публичный интернет без необходимости.

## Совместимость и версии

- Ветка `main` сохраняется как исходная версия до завершения новой разработки.
- `backup/old-before-release` — резервная копия исходной версии.
- `development/release-v2` — ветка текущей разработки.
- Отдельные Server 1 и Server 2 предназначены для раздельного развёртывания; Server 2-in-1 — альтернативный объединённый вариант.

Совместимость новых и старых версий плагина/серверов должна подтверждаться отдельными интеграционными тестами. Не смешивайте версии серверов и плагина в production без проверки протокола обмена.

## Безопасность и ограничения

CollabSync передаёт изменения между несколькими редакторами, поэтому серверная проверка личности, ролей и прав на каждое действие критически важна.

Перед публичным запуском необходимо проверить:
- подлинность Roblox-пользователя, а не доверять переданным клиентом UserId/имени;
- права на snapshot, delta, удаление и другие операции синхронизации;
- невозможность самостоятельно назначить себе роль или обойти ограничения лобби;
- безопасную конфигурацию секретов, CORS, rate limits и административных маршрутов;
- корректную работу при отключении хоста, переподключении и сетевых сбоях.

Плагин и серверы находятся в разработке. Наличие элемента в интерфейсе ещё не означает, что соответствующее ограничение полностью обеспечивается сервером. До завершения аудита считайте систему экспериментальной.

## Тестирование перед релизом

Минимальный чек-лист:
- подключить два или более аккаунта к одному лобби;
- проверить создание, подключение, выход и переподключение;
- проверить создание, изменение, перемещение и удаление объектов;
- проверить MeshPart, SpecialMesh, SurfaceAppearance, Decal, Texture и Baseplate;
- проверить Locked, Anchored, CanCollide и другие важные свойства;
- проверить чат, список участников, whitelist и настройки прав;
- проверить тестера: отметку у маркера и в чате, отказ сервера принимать его изменения Place;
- проверить оба варианта развёртывания и совместимость версий;
- проверить отказ в доступе при неверном токене и попытке отправить запрещённое действие.

- версию плагина и используемую схему серверов;
- шаги для повторения проблемы;
- ожидаемое и фактическое поведение;
- относящиеся к проблеме логи (без токенов, паролей и секретов).

Предложения по улучшениям и pull request приветствуются. Не публикуйте секреты, приватные токены или персональные данные участников.
